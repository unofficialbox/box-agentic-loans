Harborview Demo Storyboard

A borrower starts the application in the Crestline Borrower Portal; a term sheet marked up on the borrower's numbers is read against the credit policy library and the two loans Harborview already closed. Six beats, two windows, every prompt below is copy-paste.

Headless, not branded. Box holds the file, Salesforce holds the record, and the harness is whatever the customer already uses: Claude Desktop here, the same two MCP connectors from ChatGPT or Slack, the Loan Copilot inside Agentforce. Pick the surface the room lives on. Say "Claudeforce" only to explain that it is a Salesforce pilot this demo does not depend on.

Bind before use. The site URL and the borrower login below are placeholders; substitute the values for the environment you are presenting from. Everything else -- prompts, loan references, expected answers -- is portable. None of it has been run against a live org yet; expected answers come from the deterministic fixtures.

5–6 min run time Private browser beats 1 and 6 Claude Desktop beats 2–5, or any harness with both connectors Loan Copilot internal only

Preflight

Seven checks before anyone is watching. P5 to P7 are one-time setup — they stay here because a rebuilt org needs them again.

P1
Terminal

Confirm the Loan Copilot has an active version

The Copilot is not on the borrower site, so this only matters if you demo it from the internal Agentforce panel. Whatever version is active must be the one published with extract_loan_terms in its actions and default_agent_user bound to this org.

bash
sf data query -o <alias> -q "SELECT VersionNumber, Status FROM BotVersion WHERE BotDefinition.DeveloperName='LOS_Loan_Copilot' AND Status='Active'"
Expect a single row with Active. Note the version number; nothing in this repository pins it.
P2
Claude Desktop

Set the answer length

Claude Desktop decides how long an answer is, and it defaults to an essay — the beat 4 precedent question comes back as roughly 500 words and three tables. Nothing on the Salesforce side changes that: a hosted MCP server exposes tool descriptions, not a response style. Put this in the project’s custom instructions before you present, and run the beats inside that project. A fresh chat outside it carries none of these rules.

instruction
Answer in 60 words or fewer unless I ask for more. Lead with the finding. No preamble, no restating my question, no narrating which tool you called. Never print Box file IDs, folder IDs or Salesforce record IDs - use them, do not show them. Never decline a governed action on my behalf or predict that it will fail: call it and report what it says. Never apply extracted terms to a record unless I say the word confirm. Offer at most one follow-up, in one line. At most one table, only when comparing the same covenant across loans. Cite each source file once, as a link, at the end. No closing offers.
Expect beat 4 to answer in a short paragraph and one table, not a briefing note.
P3
Claude Desktop

Connect both connectors, and refresh the LOS one

The Box connector must be on as well as the LOS one. Beat 2 searches Box metadata and beat 3 opens the marked-up term sheet; neither is possible with only the LOS tools loaded. If the LOS connector was added before the Extract and Apply tools existed, open Settings → Connectors, find it, disconnect and reconnect it. Don't retype the endpoint — reuse the one already configured.

Expect both connectors listed under Context in the session, not merely enabled in Settings — a project with only LOS loaded cannot preview a document, and beat 3 falls back to reading file IDs aloud. Eight LOS tools: listLoans, findDocumentsByRisk, getLoanPackage, askLoanDocument, extractLoanTerms, applyLoanTerms, generateCommitmentLetter, prepareSignatureRequest. Beat 3 needs the two in the middle; beat 5 needs the last two.

The six beats

Beat 1 is the borrower's browser. Beats 2 through 5 run in Claude Desktop against both connectors — LOS for the loan data, Box for previews and metadata search. Beat 6 returns to the browser.

245 sec
Claude Desktop

The portfolio already knows what's risky

Uses the Box connector, enabled in P3.

prompt
Which loan documents across the portfolio are flagged critical policy risk?
Expect the marked-up term sheet, harborview-term-sheet-2026-borrower-markup.pdf, as the one Critical document. Ask for High or above and the FY2025 financial statements and the appraisal join it — the three documents beat 3 reads together.
Give it the folder id, not the folder name. Box metadata search is enterprise-wide, and a demo enterprise accumulates documents from earlier environments with the same file names and different IDs. Naming the folder does not scope it either: searching Box for “LOS-2026-Harborview” can return a LOS-2026-Harborview1 from a previous run. The ancestor_folder_id is the only thing that actually bounds the query, and findDocumentsByRisk reads it from Loans_Root_Folder_Id__c. To an audience an unscoped result reads as the wrong borrower appearing.
390 sec
Claude Desktop

Extract the terms, then read them against policy

The beat the demo exists for.

prompt
Extract the loan terms from the Harborview application package and validate them against the record, then tell me where we are outside credit policy and cite the policy library.
Expect seven extracted fields with a citation each — $4,800,000, 6.85%, 120 months, collateral $5,650,000 from the appraisal (not the borrower's $6,000,000), LTV 85%, DSCR 1.12x — and validation flagging LTV and DSCR. Then: exposure in Section 9.3 (DSCR restated to 1.10x, tested annually) and Schedule A (FF&E added at book value); policy LOS-LTV-001 (75%) with exception LOS-LTV-002 (80% with interest reserve and guaranty); policy LOS-DSCR-001 (1.25x) with exception LOS-DSCR-002 (1.15x with cash reserve); 85% / 1.12x is outside even the exceptions; Credit Risk owns the deviation.

Land it: a CRM record can't find this — the borrower's number is what was typed into it. A keyword search for "loan-to-value" returns nothing, because the markup never uses the phrase. Only reading it against a governed library does.

Then say apply those values to the record, confirm. applyLoanTerms refuses without the confirmation; with it, the allow-listed fields update and nothing else does. That is the one write in the demo, and a person just authorised it.

Nothing on that page was typed. Then show the boundary:

prompt
Send the Harborview commitment letter for signature.
Expect the action to be called, and to come back refusing, naming Underwriting. That's a state check in Apex — SIGNABLE = Approved, Commitment — not a prompt instruction. Once the loan is approved, the action still only prepares the request and hands back a URL for a person to send.
If the assistant declines without calling the action, the beat has not happened. A model that reasons "this would fail anyway" and offers alternatives is making a prompt-level refusal look like a control — the opposite of the point. Say “call it anyway and show me what it returns”. The P2 instruction tells it not to pre-judge, so this should be rare.

If someone asks

Six things to answer honestly

  • Every write is governed, and a person is in each one. The borrower's application and each document classification are written by Apex actions the borrower cannot bypass (beat 1, live-verified). extractLoanTerms reads and compares (live-verified); applyLoanTerms writes seven allow-listed fields only when a person says confirm, and refuses on a Closed or Servicing loan (refusal live-verified; a confirmed write is MT-057, the demo owner's call). Doc Gen drafts into the governed folder (live-verified) and Box Sign only prepares a request; Extract on the executed letter to set maturity and covenant dates is specified, not built.
  • This is not Claudeforce. Claudeforce is a Salesforce pilot connector for Sales Cloud that neither Box nor this demo has access to. What is shown is the headless pattern it will sit inside: Box and Salesforce as MCP connectors under whichever harness the customer uses. Do not claim compatibility with a product nobody in the room can open.
  • The Box MCP server package for Agentforce is not generally available. Its Salesforce security review is stalled on a platform bug. Demonstrate it if asked, but do not call it GA. The Loan Copilot here runs on Apex actions and does not depend on that package.
  • Where the data moves. Nowhere. Documents stay in Box; Salesforce's External Client App scopes and permission sets decide what a user may read or write on the record; Box permissions decide which content they may see; the assistant calls both and copies nothing. Say it in those words -- it is the question every customer asks.
  • The Copilot is not on the borrower site, by decision. A Service Agent runs as its assigned agent user, so it could not inherit Dana's access. An Employee Agent inherits the signed-in user's permissions instead; that's the surface where "same agent, different access" holds, and it's where the internal Loan Copilot runs.
  • The metadata tagging on seeded files is manual. Portal uploads are classified by Box AI as they land (beat 1); the seeded Harborview files were tagged by the seed script and by hand. A metadata cascade policy on the loan folder is what would make it survive the next loan.
